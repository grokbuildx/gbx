# Development architecture and subsystem contracts

Read the relevant section before changing a subsystem. This reference preserves the detailed contracts formerly embedded in the root agent instructions.

## High-Level Architecture

Detached Codex services are reused only when their protocol version matches the starting binary. Version 17 uses Responses throughout the Codex gateway. Immutable route/runtime generations and account-bound discovery continue to govern reloads. Starting a new binary replaces an older protocol on the existing loopback port. Binary upgrades, shared/independent changes and local/remote catalog source changes still replace the daemon; ordinary provider/configuration reloads do not.

The daemon polls configuration and the models.dev cache stamp once per second. It reads only its explicitly bound primary and `--with-provider` names, never follows `active_provider`. Context/effort metadata is published without replacing runtimes. Model pool, endpoint, credential or protocol changes prepare a complete new set of provider runtimes and an immutable catalog/route snapshot, persist the catalog and recovery journal off-lock, then publish the snapshot atomically. `codex.Gateway` serves requests from lock-free atomic snapshot leases (`runtimeGeneration`) through the end of each response body, including SSE; retired runtimes close after their final lease. Histories, listener, local token and catalog path survive. Failed preparation/discovery/persistence retains the last usable registry. An independent-mode default whose route was removed moves only if the TOML value is still GBX-owned; `PreviousApplied` lets crash recovery recognize both sides of that journal-before-config update. User-edited selections remain untouched.

`gbx codex start NAME --with-provider OTHER` explicitly adds account-bound providers to one gateway; repeat the flag for more. `--with-provider ''` clears additional bindings. Subsequent starts/menu switches inherit additional names unless supplied. Each `gbx/<provider>/<model>` alias binds to exactly one runtime; same-model names across providers never share credentials. `gbx codex start --refresh` requests rediscovery and runtime replacement through the authenticated control channel, without changing its URL/token. Repeated automatic refresh failures for the same config/metadata stamp back off exponentially (`5s`..`60s`), leaving the running inventory in place. A missing bound provider is an error, not permission to select another account.

`GET /v1/models` and `/v1/codex/models` serve the current merged native+GBX catalog in shared mode, or only GBX in independent mode. ETags include the catalog content and `client_version`; responses are private/revalidated, vary by authorization/account header and are bounded to 1 MiB. The merged catalog never supplies the inference allow-list. Shared mode keeps the journaled local JSON: current Codex restricts `[model_providers.openai].model_catalog_url` to HTTPS on allowed ChatGPT hosts, so a loopback URL there is invalid. Independent mode can opt into `--catalog remote`; its owned custom-provider table gets the loopback catalog URL, while effective root/default-profile `model_catalog_json` values are reversibly removed. The JSON file remains updated for `--catalog local` fallback. Explicitly disabled `features.api_key_model_discovery` is reported, never silently changed. Returning to `--shared` defaults back to the local source.

`CatalogMode` (`local` / `remote`) selects the transport only. `CatalogCapabilities.SupportsRemoteFetch` describes the configured remote-fetch path; `SupportsLiveReload` means a qualified immediate Desktop-picker reload guarantee and remains false in all current configurations. This does **not** claim that Codex cannot refresh models in the background. No mode is marked live merely because it uses a URL. The CLI/status and provider/mapping-save feedback distinguish GBX route/catalog changes from client selection: “Model configuration saved. GBX will update routes and catalog automatically; Codex may need a restart to refresh the model list.” Save feedback is shown only for an explicitly bound, running Codex provider.

|---|---|---|---|
| GBX Gateway/runtime hot update | Supported | Supported | Supported |
| GBX catalog file/server update | Supported | Supported | Supported |

Qualification on bundled **Codex `0.166.0-alpha.6`**, using one isolated app-server process, fake credentials and a local metadata-only endpoint (no inference):

1. Generated `ModelListParams` contains only `cursor`, `includeHidden` and `limit`; there is no public force-refresh argument. The corresponding handler uses `OnlineIfUncached`, so the initial A → upstream B → repeated `model/list` sequence returns A with one fetch. This establishes warm-cache reuse, not permanent caching.
2. Generated public server notifications include model rerouting/verification/safety and provider auth recovery, but no catalog-update notification. Internal model-manager watch channels exist; their existence does not establish Desktop delivery or picker behavior.
3. During a **306-second idle interval with no RPC calls**, the endpoint received one additional request; the next `model/list` in the same process returned the changed model. The matching version's source has a **270-second Online background refresh worker** and a separate **300-second cache TTL**. The observed idle fetch confirms background refresh; it should not be described as every-call refresh or attributed solely to TTL expiration. Cache-aware reads can also fetch when no valid cache remains.
4. Changing `model_providers.fixture.model_catalog_url` through `config/batchWrite` with `reloadUserConfig=true` did not immediately invalidate this process's retained catalog or fetch the new URL. That covers this provider URL mutation only; account/auth changes have separate invalidation paths, and other mutations are not ruled out.

Reproduce with `GBX_TEST_CODEX=/absolute/path/to/codex python3 integration/modelpicker/catalog_refresh.py`; use `--idle-seconds 0` for the short cache/configuration cases. The script generates the actual client schemas, records request timestamps and public notification names, rejects inference, and confines its profile to a temporary directory. Do not turn an app-server background refresh observation into a Desktop picker guarantee. A client restart remains the fallback when its picker is stale. References: [official model/list docs](https://learn.chatgpt.com/docs/app-server#models), [qualified handler](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.6/codex-rs/app-server/src/request_processors/catalog_processor.rs), [qualified background worker](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.6/codex-rs/app-server/src/models_refresh_worker.rs), [qualified cache manager](https://github.com/openai/codex/blob/rust-v0.166.0-alpha.6/codex-rs/models-manager/src/manager.rs), [Desktop remote-catalog report](https://github.com/openai/codex/issues/54881).

`gbx` launches Grok Build with the selected API-key or OAuth provider. `internal/groklaunch` prepares its process and `internal/providersession.Prepare` (or `PrepareWithOptions`, e.g. `DisableHistoryCache` for catalog-only daemons) creates a resolved copy of the provider and starts its runtime. The same runtime serves Codex. `internal/paths` centralizes `~/.gbx` data/config/cache/auth/proxy/run paths, and `internal/runtimelog` owns structured JSONL logging, retention, and usage accounting (leaving `internal/protocol` for wire/discovery helpers and shared HTTP clients).

Each runtime binds `127.0.0.1` via shared `startLoopbackServer` with a random session key. Upstream OAuth secrets live in `~/.gbx/auth/*.json` (0600) and stay bound to the configured `oauthAccountCredential`.

`gbx codex [-p name]` / `gbx codex start [name]` runs a detached **Codex-only** runtime. Runtime state remains in the existing proxy directory so active daemons and recovery journals remain manageable; `stop` / `status` manage it via a separately authenticated loopback control endpoint. `internal/proxymanager` journals the Codex overlay in `~/.gbx/proxy/state.json` before applying it. A Codex profile must already exist; open Codex once first. The daemon uses `providersession.PrepareWithOptions(..., DisableHistoryCache: true)` and sends Responses to the runtime. `gbx codex start default` stops the proxy and restores the original Codex configuration. Legacy shared-proxy journal fields are read during upgrade, stop or crash recovery to restore fields the old daemon owned. Tests use isolated profiles and fake upstreams. The separate GBX model allow-list never comes from the merged picker catalog; native requests retain their original OpenAI/ChatGPT route, while GBX requests receive only the runtime credential. Existing Codex catalogs/cache or installed bundled metadata supply native entries. In shared mode a journaled TOML overlay changes only `openai_base_url` and `model_catalog_json`, preserving comments, native login/provider and later user edits. GBX does not rely on an in-process reload of the local JSON catalog. Picker labels normally omit provider names; identical labels across attached providers add the provider name, and native-name collisions get a short GBX marker; WorkBuddy internal revisions sharing a name collapse to their formal model ID while all old routes remain valid. Explicit reasoning metadata supplies picker effort controls. The provider adapter maps the Responses reasoning effort to its upstream format. The local models.dev metadata cache supplies effort controls for recognized converted models. When a runtime publishes no reasoning levels at all, unknown models retain GPT's compatibility ladder (low, medium, high, xhigh, max, ultra, default low); known empty effort lists are never filled. A catalog already advertising levels keeps unknown models as published. GBX catalogs set `node_repl_disabled` false so Codex attaches its local Node REPL; computer use and browser control call that tool and execute on the client. macOS has an AppKit menu bar helper using the built-in JXA interpreter (no cgo/Swift build dependency); it monitors authenticated control readiness and offers provider switching plus stop. Menu names are loaded afresh without credentials; a successful switch updates active_provider and does not quit or reopen Codex, because immediate Desktop picker reload has not been qualified and a client restart remains the fallback. A failed replacement restores the previous provider before showing an error. Command-line start/switch/stop likewise leaves the client running. Provider switches use live runtime generations on the existing daemon; mode/source changes use journaled replacement. `GBX_PROXY_NO_MENUBAR=1` disables it for isolated tests/headless use. Real Codex tests in `integration/codex` require `GBX_TEST_BINARY` and `GBX_TEST_CODEX`, use fake credentials/local providers and exercise a real local tool round trip.

`gbx codex start --independent` opts into the official custom-provider path. The owned `model_providers.gbx_proxy` table uses Responses, `requires_openai_auth=false`, disabled WebSockets and a per-session loopback bearer token. The picker contains only the GBX allow-list; ordinary native/unknown model requests are rejected. The app-server account/read response is account=null / requiresOpenaiAuth=false even when a ChatGPT login is cached, so this mode does not depend on that account's quota. Do not fabricate quota responses or alter the desktop app. Restart Codex to load provider/auth/catalog changes. `--shared` restores the native OpenAI provider with the merged picker. With neither flag, starts/menu switches inherit the running mode; without a runtime journal (including after stop), startup defaults to shared. Codex 0.166+ resumes chats with their persisted model provider: independent chats bind to gbx_proxy, shared chats to openai. Removing the owned gbx_proxy block on stop/shared mode therefore makes independent chats unavailable until independent mode is restored. Cross-provider continuation requires a fork under the new provider; do not rewrite persisted chat records or claim that all chats resume across modes. See https://learn.chatgpt.com/docs/codex-sdk#resume-a-thread-without-loading-its-history. Mode changes retain the listener port. Root and active legacy-profile model/provider/catalog overrides are journaled; unrelated profile settings remain intact. A pre-existing gbx_proxy table is a collision, not an invitation to overwrite it. Stop removes the exact owned provider block; a user-edited block survives and must be renamed before reuse. Native login files and upstream account credentials are never copied into the custom provider.

Replacing a daemon for an upgrade or client mode/catalog-source change reuses the previous Codex listener port for the same Codex home. Already-open clients cache the endpoint and can retry on that address after the brief restart; generating a new random port strands both native and GBX requests. The internal replacement address accepts only an explicit `127.0.0.1` port and a bind failure must not silently pick a different port. Gateway close explicitly releases the listener even if its Serve goroutine has not registered it yet, so immediate replacement can bind synchronously. This preserves connectivity. Model/tool picker and transport settings can still require a client restart; GBX does not promise immediate Desktop refresh. Isolated process tests keep using the original URL across all three replacement paths and verify native credential separation.

Converted Codex requests with no explicit output budget use the runtime model's advertised `MaxOutputTokens`, or 32768 when unavailable; the former 4096 fallback prematurely exhausted long reasoning. Explicit client budgets remain supplied to the converter. Budget-based thinking leaves answer room within a known model capacity. Actual upstream token exhaustion still emits `response.incomplete` / `max_output_tokens`, never a fabricated completed response. Native Responses routes pass through unchanged.

Converted Codex models and `gpt`/`codex` OAuth routes (`CodexNativeTools`) advertise `supports_search_tool`; `grok`/`xai` OAuth routes through `serveBridge` (gaining `code_mode_only`, `tool_search`, local `gbx1:` compaction and context migration while the `xai` runtime flattens `exec` custom tools). `internal/oauthproxy/responses_request.go` translates client-executed `tool_search`, `computer`/`computer_use_preview`, `shell`, `local_shell` and `apply_patch` tools into function tools, and the response assembler restores their native `*_call` items. Codex searches its local tool catalog and returns `tool_search_output`; the adapter replays that result and loads only the selected definitions, preserving namespace and custom-tool formats. Deferred definitions stay unloaded when client search is available. GBX owns no search index or discovery loop, and only Codex executes actual tools under its normal permissions. Discovered definitions come from the current request/history, never other sessions/accounts. Generic `openai_responses` API-key gateways remain passthrough with `supports_search_tool: false` and do not gain an adapter capability declaration. Real-client tests use fake upstreams and cover search, tool execution and permission denial; reliable use by a particular upstream model still needs model testing. Synthetic request-byte reductions are not measured production token savings.

Cross-model history is normalized only at the backend boundary. Before native Responses forwarding, `history_interop.go` removes GBX reasoning items and unencrypted reasoning from stateless requests and turns GBX compaction summaries into ordinary user history. Native encrypted reasoning remains unchanged; translated backends skip opaque native reasoning while retaining messages and tool results. Local compaction (`compactionItems`) summarizes `function_call*`, `custom_tool_call*`, `tool_search_*`, `computer_call*`, `shell_call*`, `local_shell_call*` and `apply_patch_call*` records as plain text and replaces inline image/screenshot parts (`input_image`, `computer_screenshot`, `data:image/...`) in tool outputs and messages with `[image omitted]` so multi-screenshot Computer Use sessions stay within compaction context budgets. Native encrypted compaction cannot be decoded locally. Translated backends may recover a bounded excerpt of the matching local chat transcript as described below; missing or mismatched history is rejected. Keep native routing, credentials and `store` unchanged. Real-client tests resume one conversation GBX → native → GBX without model calls outside local fixtures.

`context_migration.go` handles opaque native compaction only on converted routes. A UUID chat ID from Codex client metadata/headers, matching session metadata and the exact compaction ciphertext must identify the same local rollout checkpoint; a supplied account header must also match. Only files for that ID under CODEX_HOME sessions/archived_sessions are considered, with symlinks confined to the Codex home. Fork/base history from another chat, missing base records, mismatches and missing transcripts fail explicitly. No session files are rewritten and no credentials or reasoning traces are recovered. The adapter reads visible user/assistant/tool text (including `computer_call*`, `shell_call*`, `local_shell_call*` and `apply_patch_call*`, replacing inline screenshot/image data with `[image omitted]`) up to the matched checkpoint, keeping a bounded beginning/recent excerpt (16K/48K bytes, individual records excerpted at 4K, at most 32 files / 128MiB). This is not decryption or lossless semantic summarization. Images and older/lengthy details may be missing; a visible GBX migration notice accompanies the subsequent answer. Cached excerpts/notices use bounded, owner/session-scoped memory and survive only the daemon lifetime. Native Responses traffic remains unchanged.

On a model downshift, Codex can compact using the previous native model name. In independent mode only a native entry from the source catalog may delegate that internal compaction to the configured GBX default route. Recognize explicit compact endpoints, compaction_trigger or client turn metadata request_kind=compaction with no tools; use the target model's own default effort. This does not add native names to the ordinary routing allow-list. The original client still owns the summarization request, normal model call, tool registry and permissions. Real-client tests cover shared → independent resume with native encrypted compaction, a fixed chat ID, retained visible goals and no opaque/undeclared-tool replay.

Translated history also follows the current tool declarations. When a model/tool-mode switch retires a tool, replay its past call and result as labeled history text, preserving image content; do not send an undeclared function call or restore the retired capability. Desktop-delivered named tool outputs without `call_id` (including `codex_app.send_message_to_thread`) are notifications, not results of an invented model call. Nameless, uncorrelated outputs still fail validation. Provider calls outside the current registry remain rejected; errors include bounded tool names for diagnosis, never arguments. A real-client regression resumes a classic MCP conversation in code mode and checks that the previous result survives while JavaScript invokes the client MCP again.

The Codex tool harness also follows the installed native catalog. `Plan` (and `RefreshNativeCatalog` on forced proxy reload) calls `inheritClientToolMode`: when a genuine native entry advertises `tool_mode: code_mode_only`, translated GBX entries and `gpt`/`codex` OAuth entries (`CodexNativeTools`) inherit that mode, its `shell_type` (such as `unified_exec`), and its Node REPL review requirement. Stale GBX entries never supply the template; older catalogs and generic `openai_responses` passthrough entries keep their existing mode. `FindExecutable` resolves desktop `codex-cli/codex-package.json` (`entrypoint`) and `codex-cli/bin/codex` layouts alongside legacy app-bundle paths; `nativeCatalog` recovers bundled capabilities when a real cache (`client_version` set) predates `code_mode_only` or when `model_catalog_json` holds only leftover `gbx/*` entries, while keeping synthetic test caches (`client_version` omitted) strictly isolated from host binaries. Node REPL enablement and image input alone do not select the desktop tool harness. The proxy still translates code-mode custom calls to ordinary function tools; JavaScript, MCP/computer tools and permission checks execute in the Codex client. A real-client regression checks that catalog inheritance enables the exec/wait harness and that JavaScript can invoke a local MCP fixture and return its result.

Image capability travels in `protocol.ModelInfo.InputModalities`, including Qoder `is_vl`, WorkBuddy `supportsImages`, Responses/model-catalog modality fields, and `models.dev` modality backfills for recognized IDs when runtime metadata omits modalities (alongside missing `MaxOutputTokens`). Only models that advertise images receive the Codex `"image"` modality and `supports_image_detail_original: true`; unknown models stay text-only (`["text"]`, `supports_image_detail_original: false`). `RefreshCatalog` persists `input_modalities` and `supports_image_detail_original` and retains discovered vision metadata if an optional local cache is later damaged. Keep `node_repl_disabled` false. Responses function, custom and computer tool result arrays retain typed image parts (`input_image`, `computer_screenshot`, parameterized data URLs and magic-byte-sniffed base64 screenshots) through the provider adapter. Qoder and Chat put tool screenshots in a user message after all tool replies, without duplicating base64 as tool text. Real-client screenshot tests check the image gate and image round trip; they do not prove a model can reliably operate a desktop.

### Protocol ownership (`internal/oauthproxy`)

Canonical notes: `internal/oauthproxy/doc.go`. Do not reintroduce an external provider process (no qodercli, no Codex CLI).

Converted Codex requests explain the mapping from logical names in client instructions to the current flattened function declarations, including the JSON `input` wrapper for custom tools. Executor documentation and historical calls never authorize additional functions; the response bridge still rejects every undeclared name.

Converted Codex tools keep short, valid unnamespaced names such as `exec`, `wait` and `tool_search`. Namespaced/unsafe/long names retain deterministic hash aliases, and root names already ending in the reserved 12-hex hash suffix are hashed too so they cannot impersonate those aliases. Chat conversion binds responses to the current tool declarations. Streamed function names are assembled from exact declaration prefixes, accepting repeated/cumulative complete names only when the interpretation is unique. Validate every name in a parallel batch before emitting its first call. Undeclared, incomplete, ambiguous or damaged names fail without exposing embedded reasoning/DSML as diagnostics; neither the parser nor Codex bridge guesses a replacement or executes embedded protocol text. This is a compatibility fix and validation boundary, not a guarantee that an upstream model will always generate a valid call. Generation failures are never silently retried after partial output.

Loopback `/v1/responses` wraps every runtime with `withResponsesHistory` (`responses_history.go`, skipped when `DisableHistoryCache` is set): `previous_response_id` expands locally from a bounded per-runtime cache (`64` entries / `64 MiB` / `30m` TTL, returning HTTP `400` `previous_response_not_found` when uncached) while upstream `codex_responses` and `xai` requests keep `store=false`, strip unencrypted or non-Codex `rs_gbx_` reasoning items before replay, and (on `xai`) clamp or strip unsupported `reasoning.effort` values against the xAI catalog. Loopback `/v1/chat/completions` (`chat_front.go`) also translates `custom_tool_call` outputs into function `tool_calls`, and `/v1/models` (`serveModelListWithDetails`) publishes `api_backend: "responses"`, `context_window`, `max_output_tokens`, strictly documented `input_modalities` (never inventing `"image"` for text-only or unknown models), and both Codex/Grok reasoning effort metadata (`supported_reasoning_levels`, `supports_reasoning_effort`, `reasoning_efforts` filtering Codex `"ultra"`, and `reasoning_effort_server_default`, with `models.dev` fallback).

Shared 429/5xx fast retry is `retry.go` (at most 500ms + 1s; a longer `Retry-After` returns immediately for the client to honor). Credentialed probe and OAuth HTTP clients (`protocol.NewProbeHTTPClient`, `oauthproxy.newCredentialHTTPClient` / `newTimedCredentialHTTPClient`) refuse cross-origin redirects so `Authorization`, `Cookie`, `Proxy-Authorization`, and `X-Api-Key` headers are never forwarded across origins, Qoder and WorkBuddy scrub login query values from network errors, and external image/resource fetchers reject non-public/SSRF targets at dial time and across redirects. Qoder reads exactly its bound credential and rechecks type/disabled under the refresh lock. Per-backend 401 refresh happens **inside** one attempt. Kiro has its own 1/2/4s loop; WorkBuddy runs single-hop inside `openai_chat_runtime.go` so retries never nest.

Converted Codex models resolve effort controls from `~/.gbx/cache/modelsdev.json` via `internal/modelsdev.CachedIndex`; no model database is embedded in the binary. OAuth success and confirmed `gbx set` save refresh the public models.dev API with a five-second budget; `gbx set --refresh-models` refreshes metadata without opening the editor or changing providers. The models.dev provider picker uses the same network-first/offline-cache path. HTTP ETags avoid redownloading unchanged data. Validate a complete response before atomically replacing the last good snapshot; a separate hash-bound validator file cannot attach an ETag to mismatched JSON after a crash. Updates use a cross-process lock. Network/invalid-data failures fall back to a valid offline copy; without one, authentication/configuration still succeeds and Codex retains compatibility defaults. Models.dev metadata is never downloaded by proxies on startup or during inference. They lazily build one immutable index per unchanged local snapshot. The running daemon watches local cache/config stamps and refreshes catalog-only settings without replacing its runtime; The client may need a restart to refresh its picker. Explicit `codex start` handles binary/protocol upgrades on the same port; provider changes use the live registry.

Exact `modelsDevProvider` (or OAuth provider ID) entries take precedence, then canonical model-owner entries, then `opencode-go` / `opencode` reference rows, then unambiguous other rows. IDs and exact display names match without fuzzy version stripping. Conflicting equal-priority entries are not merged. This index supplies metadata only: a deprecated reference row can still describe a live upstream route, and it never creates routes. `reasoning_options` of type `effort` supplies tiers; thinking switches (`none` / `toggle`) and token budgets are not invented slider rungs. A known empty effort list prevents GPT compatibility defaults. Unknown models keep existing fallback behavior, and native Responses metadata stays on its own path. Keep an existing valid default; otherwise choose low if available, or the first tier. models.dev currently supplies no default effort. WorkBuddy's discovery still owns available IDs, labels, prices and images; its per-model reasoning detail is not consumed. `xhigh` and `max` survive Responses → Chat `reasoning_effort` conversion.

Qoder can return HTTP 200 with a stream-envelope `403 / 10605 / RESOURCE_LIMIT`, including `isQueued=false` and a positive `retryAfterSeconds`. Treat that metadata as a temporary resource limit, not an authentication failure. Qoder waits for actual model output before starting the Responses stream, so an early envelope rejection becomes HTTP 429 with `Retry-After`; the Codex bridge preserves both the header and error type. After partial output, emit a concise typed stream error without replaying the request. Do not add another provider retry loop or account fallback. Tests cover queued/nonqueued capacity, heartbeat frames, partial output, and ordinary permission denials separately.

`gbx set` Auto Configure only GETs `/models` metadata for generic gateways. OAuth subscriptions have no Auto Configure row at all: `configureOAuthRuntime` copies the catalog straight from the loopback runtime (`runtime.Models()`), so a subscription is never probed as a generic endpoint. Model-pool `[1m]` suffixes on `Provider.Model` survive re-detection (`preserveOneMMarkers`), while unmarked models never gain an implicit `[1m]` marker. Legacy Claude tier slot mappings (`Opus`/`Sonnet`/`Haiku`/`Fable`/`Custom`/`Subagent`) and `gbx map` are retired; legacy slot entries fold into `Provider.Model` on load and are omitted on save.

### Config, launch, TUI

- `internal/config` reads `~/.gbx/config.yaml`. Write through `config.Update(fn)`, which locks, reloads and atomically writes the file with mode 0600.
- `default` launches Grok Build with its own login. A configured provider starts a Responses runtime and passes its loopback URL and session key through `GROK_MODELS_BASE_URL` and `XAI_API_KEY`. An isolated temporary auth file prevents a cached Grok login from taking precedence. Provider environment variables cannot override routing or credentials; `browserEnvironment` uses a fail-closed allowlist of safe non-routing `GROK_*` feature vars (`GROK_CLAUDE_SKILLS_ENABLED`, `GROK_CURSOR_SKILLS_ENABLED`, `GROK_SUBAGENTS`, `GROK_SUBAGENTS_MAX_DEPTH`, `GROK_MEMORY`, and `GROK_HOME` when unprofiled) and seeds `GROK_SANDBOX=workspace` plus `GROK_DISABLE_AUTOUPDATER=1`. The web launcher then applies only the conversation’s validated, pinned sandbox selection (`workspace`, `gbx_worktree` for session worktrees, or an explicitly selected `off`); provider environment variables never select the sandbox.
- `GROK_CONFIG` emits only Grok-supported schema keys: `models.default`, `models.allowed_models` (including runtime-discovered IDs/display names plus stripped and `[1m]` IDs), helper model pins (`web_search`, `image_description`, `session_summary`, `prompt_suggestion`), normalized `default_reasoning_effort` when configured (`ultra` → `max`), and `features.subagent_model_inheritance: true`. `gbx [--provider <name>] grok <subcmd>` strips the `grok` escape keyword cleanly, local non-model Grok invocations (`doctor`, `mcp`, `plugin`, `sessions`, `usage`, `version`, `-v`, `--help`) skip starting a runtime, and `bypass_mode` never injects `--always-approve` onto Grok subcommands even after global flags. Grok's own `--agent` passes through, and `--json` / `--output-format json` suppresses the GBX launch banner on stderr.
- Providers may pin `Provider.DefaultModel` (`defaultModel` in config/Web UI) via `gbx set [-m|--default-model <id>] [provider]`, `gbx provider set`, or the `gbx set` TUI `Default Model` stepper/picker overlay (including `[1m]` toggles via `Tab` and auto-resetting dropped models on re-detection). `RuntimeModelSpec` promotes `DefaultModel` to the front of the model list, and `provider.EffectiveDefaultModel`, `groklaunch`, `codex`, `gbx ls`, `gbx doctor`, and `gbx serve` honor it consistently.
- The runtime rejects retired single-protocol Messages providers, Claude OAuth, Zed OAuth, and Gemini/Antigravity OAuth entries without replacing or deleting their saved credentials. Mixed models.dev gateways route `@ai-sdk/anthropic` models (`ModelProtocols` value `anthropic`) through the GBX Messages adapter (`anthropic_messages_*.go`): Responses requests become streaming `POST {base}/messages` calls with `x-api-key` and `anthropic-version`, where `{base}` is the model's models.dev `provider.api` (`ModelEndpoints`) or the provider endpoint. Messages SSE is decoded through the shared assembler. Thinking signatures and redacted thinking travel in `encrypted_content` behind `gbx-anthropic:` / `gbx-anthropic-redacted:` and are replayed only to Messages routes; when a tool-loop turn lacks signed thinking or the tool choice is forced, thinking is turned off for that request. A legacy default Claude selection requires an explicit `gbx use default` before using Grok Build’s native login.
- The `gbx set` TUI lets a user choose Chat Completions or Responses for an API-key gateway. Metadata discovery checks the shared `/models` endpoint and preserves an explicit Responses choice. Cursor scroll anchoring and mouse hit-testing resolve directly from structured `bodyLine` metadata and shared `bodyLayoutGeometry` (no offline `tui.Sprint` re-render or ANSI text scraping), and background detection/verification/refresh tasks bind to cancellable lifecycle contexts.

### Browser sessions

`gbx serve` serves the embedded workspace Web UI (`internal/webui/frontend`, built into `internal/webui/web`) and authenticated REST/SSE API on `127.0.0.1` (or a mode-`0600` Unix socket via `--socket`, staging inside a `0700` temporary directory before atomic rename whenever the parent directory is shared, where filesystem permissions replace bearer-token auth). TCP mode requires a bearer token (`--token`, `GBX_SERVE_TOKEN`, or a per-server random secret delivered via the launch URL `#fragment` and stored by the browser); `cmd/serve.go` unsets `GBX_SERVE_TOKEN` after reading it and `groklaunch.ScrubServeEnv` scrubs `GBX_SERVE_*` from every spawned child (`grok`, `git`, `mcp`, PTY shell). `internal/webui` enforces a loopback `Host`, same-machine `Origin`, and `Content-Type: application/json` (or multipart on `/uploads`) on mutations.

Each turn starts a dedicated `grok agent --no-leader stdio` ACP v1 subprocess with the conversation’s pinned `GROK_SANDBOX` (`workspace` by default, `gbx_worktree` in a sandboxed session worktree, or explicitly selected `off`; `--always-approve` in `bypassPermissions`, or ACP `NewSession`/`LoadSession` `_meta` + `SetSessionMode` for `bypassPermissions`, `auto`, `plan`, and `default`, auto-approving `ToolKindEdit` in `acceptEdits` and forwarding `Answers`/`Message` metadata on interactive `RequestPermission` outcomes). Grok native tool names (`ask_user_question`, `exit_plan_mode`, `spawn_subagent`, `skill`, `todo_write`, `list_dir`, `search_replace`/`hashline_edit`/`apply_patch`, `run_terminal_command`), subagent `_meta`/`variant` canonical identity preservation, `_x.ai/session_notification` (live) and `_x.ai/session/update` (legacy/persisted) (`subagent_spawned`/`subagent_finished`) lifecycle & usage correlation, and `_x.ai/mcp/list` connectors normalize into the Web UI event stream. Configured providers run through `groklaunch.PrepareBrowserWithSession` backed by a per-server `runtimePool` (`10m` idle eviction timer, config-fingerprint and per-provider/global generation validation, refcounted retirement, exclusive-turn fallback usage accounting, and invalidation on provider config, OAuth login, or cloud pull changes), passing a warm loopback Responses runtime URL, per-session inference key, and isolated temporary auth file while keeping provider settings and upstream credentials inside GBX; `default` uses Grok Build's own `~/.grok` login (refusing a retired legacy Claude default until `gbx use default`). Prior turns resume via ACP `LoadSession` while suppressing replayed history chunks already persisted in `~/.gbx/serve/sessions/<id>/events.jsonl` and syncing `SetSessionConfigOption` (`model` and clamped `reasoning_effort`, resetting back to managed provider/model defaults when the WebUI selects Auto/Default on resume); one turn at a time owns a session, `session/cancel` resolves pending permission prompts cleanly before teardown, and process signaling guards against PID reuse after wait/reap. `SessionStore` maintains in-memory session/share indexes with bounded open-session LRU eviction (`maxOpenSessions = 128`, preserving active/subscribed sessions), strict `Store.mu -> Session.mu` lock ordering, `beginDelete` tombstoning before worktree teardown, and a bounded per-session tail cache (`sessionTailCapacity`) whose append handle closes after each turn exit so SSE reconnects and health/share lookups stay O(1) without leaking FDs or rescanning disk. Frontend WebUI handles `/effort` client-side, applies streaming events incrementally via `ThreadReducer` with lazy-loaded secondary panels and curated CodeMirror grammars, fetches `GET /api/providers/{name}/models` with cached/live runtime catalogs, reads `defaultProvider`/`defaultModel`/`defaultEffort`/`defaultEffortLevels` from `GET /api/capabilities`, and shares effort ladder/default resolution with `/v1/models` via `oauthproxy.ResolveGrokModelEffort` and `oauthproxy.StaticProviderModelDetails` (alongside `models.dev` metadata fallback and explicit variant exclusions).

Subagent process events retain their child ACP session ID. The Web UI runner registers descendants only from lifecycle notifications on the root or a registered child, then routes thought/message chunks and tool events through a separate translator per child. Child tool IDs are namespaced and attached to their owning spawn call; nested children stay scoped, and child usage/commands never overwrite root state. Events wait for a known spawn-call association, are persisted in the parent browser timeline for replay, and late child chunks preserve terminal task status. `subagent_progress` updates carry running token/tool/time statistics.

The composer keeps follow-up messages in a per-session browser queue. “Send now” posts `steer: true`: GBX reserves the next turn, cancels and settles the current ACP worker, then resumes the same agent session with the selected text and attachments. The reservation excludes competing sends/schedules and is cancelled by Stop or server shutdown. Failed sends retain the queued message for explicit retry; accepted sends remove it only after the server response. Other queued messages retain FIFO order.

`gbx serve --sandbox workspace|off` sets the initial sandbox default for **new conversations** without writing configuration. With the flag omitted, `serve_sandbox` in the GBX config supplies the default, then `workspace` when unset; unsupported values fail validation. Settings → General updates this running server’s new-conversation default and persists it through `config.Update`; a later server start with an explicit flag overrides that saved value again. Other running servers retain their current default. `/api/config.serveSandbox` and `/api/capabilities.defaultSandbox` publish this server’s selection; `/api/config.savedServeSandbox` reports the persisted default so the page can explicitly save a CLI-only override. A transition to `off` (including persisting a CLI-only `off` selection) requires `confirmSandboxOff: true` at the config endpoint; the page confirms the expanded file-write/process access before saving. Tool approval (`bypass`, session permission mode) stays independent. The CLI warns when the selected default is off.

Session metadata snapshots `sandbox` at creation; missing legacy values mean `workspace`. Before the first launch, `sandboxProfile` pins the resolved Grok profile with persistence-before-publication; later turns reject changed/missing worktree profiles or cross-mode specs before starting ACP. Existing conversation sandbox patches return a conflict directing users to change Settings and start a new conversation. Settings changes, provider/approval changes, schedules and restarts preserve the pinned mode and `AgentSessionID`, without clearing history or rewriting upstream sessions. The page displays the conversation’s own selection, or the new-conversation default before creation. Upstream CLI resume documents profile immutability, while the pinned ACP `LoadSession` path does not validate the saved profile; GBX therefore checks its own pin. `off` disables the sandbox requested by this launcher; it cannot remove inherited OS restrictions, and upstream managed policy can still require a sandbox. `workspace` primarily constrains writes and process operations and permits broad reads; the control is not a data-read isolation guarantee. Isolated fake-ACP and launcher tests cover the two settings, native/configured providers, worktrees, persistence failure, confirmation, and resume boundaries without model calls.

Alongside chat, `internal/webui` serves multi-workspace management, workspace file browsing/editing with SHA-256 conflict checks (rejecting `.git` path segments case-insensitively pre- and post-symlink resolution and bounding file reads/writes), Git status/diff/stage/commit/branch inspection (always passing `-c core.fsmonitor=false -c core.hooksPath=/dev/null` with scrubbed `GBX_SERVE_*` env), isolated session Git worktrees (`~/.gbx/serve/worktrees/<session>`, copying untracked local overlays such as `AGENTS.local.md`, `CLAUDE.local.md`, `.mcp.json`, `.grok/{settings.local.json,config.local.toml,sandbox.toml,skills,agents,commands}`, `.claude/settings.local.json`, and `.agents/skills`, recording validated relative overlay paths in store-owned `<store-root>/.worktree-overlays/<wsID>/<name>` rather than the sandbox-writable `.git` dir, verifying cleanliness before removing overlays via `os.OpenRoot` with backup/restore on removal failure, and synthesizing `[profiles.gbx_worktree]` in `<worktree>/.grok/sandbox.toml` scoped strictly to the repo's `.git` common dir), an optional PTY web terminal (`--shell` / `--no-shell`), read-only share snapshots, prompt schedules, OAuth subscription logins, MCP connector management via sanitized `grok mcp` subprocesses, user (`~/.grok/AGENTS.md`) and project (`AGENTS.md`) instruction editors, and `gbx cloud` sync.

The chat composer always displays context usage and capacity below the route controls, alongside sandbox status. Before the current turn reports usage it displays an awaiting-usage state. ACP usage updates carry the actual window in the `context` event; older events and unreported usage fall back to the provider context preset or effective model’s `[1m]`/`-1m` suffix (otherwise 200K). Zero usage is a valid measurement.

### i18n layering

User-facing Chinese lives in `cmd/` via `locale.T`. `internal/` must not contain Chinese string literals (`internal/protocol/no_chinese_strings_test.go`); `internal/locale` is the exception.

### Cloud sync

`internal/cloudsync` encrypts `config.yaml` + `auth/*.json` to iCloud / Google Drive under `gbx cloud ...` only (registry v2 in `~/.gbx/cloud`; no v1 layout, passphrase, Keychain, recovery-key or pairing modes). The Desktop OAuth client (Cloud project `93551281893`) is not in source: release ldflags inject `cloudsync.googleOAuthClientID/Secret`; PKCE is the real auth boundary; `appDataFolder` belongs to the Cloud project. The random profile key is stored in the cloud `profile.json` (`account_key`), so `loginFirstRemote` on a new device opens the account's profile (or creates one) with nothing but a login. `--no-browser` (default when `headlessHost()`: SSH, Cloud Shell, Linux without a display) prints the authorization URL and reads the redirected `127.0.0.1` address pasted back (`cloudsync.WithPastedRedirect`), still with the Desktop client + PKCE. Do not reintroduce the OAuth device flow: Google rejects `drive.appdata` there (`invalid_scope`) despite its docs, and `appDataFolder` is per Cloud project, so any other client would see different data.

## Product facts that affect code changes

gbx launches Grok Build and provides a protocol proxy for Grok Build and Codex. Extra CLI arguments reach Grok Build.

Canonical OAuth provider specs (public names, aliases, endpoints, fast-mode support, discovery intervals, reserved names) live in `internal/provider/specs.go`. OAuth public names: `gpt` `grok` `qoder` `kimi` `kiro` `workbuddy` `workbuddycn` `autoclaw` `cursor` (`claude`, `zed`, `gemini`, `antigravity`, and `gemini-cli` are retired). `workbuddy` is www.workbuddy.ai and `workbuddycn` is www.workbuddy.cn: same plugin API and chat protocol, different origin and credential `type` (see `workbuddyDeployment`). Static default model pools for OAuth providers without live `/models` discovery (`kimi`, `kiro`) live in `internal/provider/oauth_defaults.go` and the respective `internal/oauthproxy` runtimes.

`bypass` injects `--always-approve`, except when `--permission-mode` is given or the first arg is a Grok subcommand. Provider management lives under `gbx provider` (with root shortcuts `gbx set`, `gbx ls`, `gbx use`, and `gbx preview`) and sync under `gbx cloud`. `gbx doctor` is read-only and bills nothing without `--probe`. `internal/selfupdate` owns release download/checksum verification (`SHA256SUMS`), atomic binary replacement, and `npm`/`go` upgrade dispatch (shared by `gbx update` and `gbx serve`); `--method self|npm|go` is required off a TTY.
